# Internationalization

Latticefolk treats language as simulation-facing data, not only UI decoration.

## Supported locales

| Locale | UI | Versioned authored dialogue seed |
| --- | --- | --- |
| `zh-CN` | yes | yes |
| `en` | yes | yes |
| `ja` | yes | yes |
| `es` | yes | yes |

The selected locale is stored in browser local storage and is sent with dialogue requests. `DialogueStore` isolates candidate retrieval by locale before Jev/fallback selection, preventing mixed-language candidate sets.

## UI strings

UI strings live in `src/i18n.ts`. Add a key to the English dictionary first, then provide translations in all supported dictionaries. English is the fallback for missing keys.

Do not place provider prompts or simulation identifiers in translated UI files. Internal action IDs such as `harvest`, `trade`, and `sleep` remain stable across locales.

## Dialogue corpus

Versioned authored seed data lives in:

```text
data/dialogue-seed.multilingual.jsonl
```

Each entry may include:

```json
{
  "id": "seed-en-001",
  "locale": "en",
  "kind": "line",
  "text": "Morning.",
  "tags": ["morning"],
  "intents": ["greet"],
  "moods": ["calm"],
  "roles": ["farmer"],
  "weight": 1
}
```

Runtime/user-imported dialogue stays in the ignored `data/dialogue.jsonl`. Versioned supplemental seeds are merged by stable ID at startup, so repository updates do not require deleting user corpora.

## Adding a language

1. Extend `LocaleCode` in `src/types.ts`.
2. Add the locale to `SUPPORTED_LOCALES` and the dictionary in `src/i18n.ts`.
3. Add authored line and fragment seeds to `data/dialogue-seed.multilingual.jsonl`.
4. Add a localized project overview under `docs/README.<locale>.md`.
5. Verify that one conversation never mixes candidate locales.
6. Update this document and the root README language navigation.

Translations should preserve the character intent and gameplay meaning rather than mechanically mirror word order.
